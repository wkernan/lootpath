## 1. What Lootpath is

**One sentence:** Lootpath puts QE Live's gear answers inside World of Warcraft, next to the loot they are about.

**The three promises, on one in-game frame:**
1. **Equip Now** - what you should be wearing right now, from what you own, with one-click equip.
2. **Upgrade Map** - for each gear slot, which dungeon boss or raid boss drops a candidate, and (where QE Live has ranked it) how much better it is.
3. **Vault** - which Great Vault option to take this week.

**The product rule, above every other rule:** **Lootpath never computes a healer value.** Every healing number on screen is QE Live's, transported unchanged from its export. Lootpath's own work is the scanner (gear, bags, bank, vault), the loot map (Encounter Journal walk), matching, and display. No network, no backend, no behaviour in combat, no estimate of its own to fill a gap.

**Who it is for, in order:** the owner (MVP = the owner alone, on one character); then healers generally; DPS via Raidbots/MythicSim output is a later extension of the same import interface, not an MVP goal.

**Why this exists:** the audience's whole gearing loop today is alt-tab: `/simc` in game, paste into QE Live in a browser, read the answer there, alt-tab back and try to remember it at the vault or when a drop appears. QE Live is right about the math; everything around the math happens where the game cannot see it. Mr. Mythical solves this in-game for DPS with a SimulationCraft-trained model; SimulationCraft cannot model healing, so no healer equivalent could be built that way. Lootpath is "Mr. Mythical for healers" with QE Live as the brain.

## 5. Data flow (the round-trip)

1. In game: SimulationCraft addon `/simc` (includes equipped, bags, and vault when available) - copy.
2. Browser: run **Top Gear** (M+ by default), Export > **Download JSON**. **Until the fork's PR lands upstream that control exists only on the fork**, so the owner runs it locally (`npm start` in `c:\Code\qe-live-fork`) rather than on questionablyepic.com/live.
3. In game: `/lootpath`, paste the JSON text into the editbox. `QEImport` validates (schema, version 1, Retail) and stores the verdict in SavedVariables with its `exportedAt`.
4. `Inventory` scans; `Journal` walks (cached); `Vault` reads; `Match` joins verdict to inventory and journal by item key.
5. Three panels render. Equip Now can equip out of combat.

Constraints that shape it: addons have **no network** and **cannot read files** (hence paste); SavedVariables flush **only on `/reload` or logout**; secret values apply in combat/encounters/M+/PvP (spike-verified they lift out of combat; the guard stays on every read regardless); the bank is readable only while the bank frame is open.

## 6. Architecture

One shipped package `Lootpath/` (what the packager zips) plus `spec/` (tests) and `tools/` (dev scripts). One namespace table `ns` shared via `.toc` load order; modules register on `ns`; no globals except the slash handler.

| Module | Responsibility | Interface (contract) | Testable headless? |
|---|---|---|---|
| `Core.lua` (shipped M0-1) | lifecycle, events, `/lootpath` dispatcher (`capture <name>`, `capture`, `capture wipe`, `status`, `help`), AceDB SavedVariables, `ns.Safe(value)` secret guard, `ns.CopyRaw(table)` guarded deep copy (secret, cycle, depth 10, 50k nodes, UI objects), `ns.Probe(fn, ...)` pcall-to-positional-table, `ns.ItemKey(id, bonusIDs)`, `ns.RegisterCapture/RunCapture` | `ItemKey` = `"<itemID>:<sorted bonusIDs joined by :>"`, bare `"<itemID>"` with none, `nil` for garbage; ONE definition used by QEImport and Match. `RunCapture(name, onComplete, args)` refuses in combat (`{ok=false, reason="combat"}`), before the DB exists, for unknown names, and while another capture is running. A capture registered `{ async = true }` is handed `finish(data, failure)` instead of returning data, answers `{ok=true, pending=true}` at once, and is abandoned after `ns.CAPTURE_TIMEOUT_SECONDS` (180) if it never calls back; `finish` counts only once (M3-1) | yes (`spec/core_spec.lua`) |
| `Captures.lua` (shipped M0-1) | `/lootpath capture env`, `inventory`, `vault` raw dumps | snapshot `{ name, capturedAt, capturedAtLocal, build, addonVersion, sawSecret, durationMs, data }` appended to `db.global.captures[name]`. Reads only; every client function called is named in the file (bank predicates are an allow-list) - never a namespace walk, because `C_Bank` also moves items and money | yes (`spec/captures_spec.lua`, over the stub) |
| `Modules/Inventory.lua` (shipped M1-1) | equipped + owned bags 0..5 + bank tabs (only while `C_Bank.CanViewBank` says so) -> records | `ns.Inventory:Scan()` -> `{ ok = true, records, bankAvailable, secretsSeen }` or `{ ok = false, reason = "combat" }`; record `{ key, itemID, link, itemLevel, bonusIDs (sorted), slot, equipLoc, location = equipped/bag/bank, bag, slotIndex, name, quality }`. **`slot` uses QE Live's vocabulary** (`Head`, `Neck`, `Shoulder`, `Back`, `Chest`, `Wrist`, `Hands`, `Waist`, `Legs`, `Feet`, `Finger`, `Trinket`, `1H Weapon`, `2H Weapon`, `Offhand`, `Shield`, read from `TopGearExports.ts`), not the issue's `HEAD` style, because Match groups per slot against the export. Every read passes `ns.Safe`; a secret is dropped and counted. `ns.ParseItemLink` (Core) is the one link parser | yes: `spec/inventory_spec.lua` replays the transcript through the stub and compares to golden fixtures under `spec/fixtures/expected/` |

A golden guards regressions; the field-by-field tests against the raw returns are what prove correctness.
- **2026-09-06 - The sign convention has one definition in code**: `ns.QEImport.ALT_WORSE_SCORE_PERCENT_SIGN = 1`, `ALT_WORSE_HPS_DIFFERENCE_SIGN = -1`, and `ns.QEImport.AlternativeIsBetter(alt)`. M2-2 and M3-3 read the direction from that predicate and never from their own arithmetic, because getting the sign backwards is this module's whole failure mode. The spec pins the same two constants independently.
- **2026-09-06 - `version` must be the JSON number `1`.** A string `"1"` is refused rather than coerced: a changed type means the schema moved, and the pin exists to fail loudly rather than wrongly (extends the 2026-09-05 version-pin decision).
- **2026-09-06 - The verdict keeps `topSet.order` and a per-item `count`.** A map keyed by item key has no order and collapses a matched pair of identical rings into one entry; `order` (keys in the export's own order, duplicates repeated) and `count` keep both facts. QE Live's exporter has a commit named "handle duplicates", so duplicates are real.
- **2026-09-06 - Vault items are harvested from alternatives as well as the top set.** A vault option QE Live ranked *below* the top set appears only in a differential; excluding it would hide exactly the option the Vault panel must talk about.
- **2026-09-06 - `QEImport.Parse` carries no combat guard.** It is pure Lua over a pasted string; its one client read is `UnitName("player")` for the name-mismatch warning, and that passes `ns.Safe`. The combat rule binds the UI (M2-2) and the scanners, not a string parser.
- **2026-09-06 - Captures can be asynchronous.** `ns.RegisterCapture(name, help, run, { async = true })` hands `run` a `finish(data, failure)` callback and `RunCapture` answers `{ok=true, pending=true}`; the snapshot is stored when `finish` is called, and `finish` counts only once. The Encounter Journal loads loot only after `EJ_LOOT_DATA_RECIEVED`, so `capture journal` cannot be one synchronous call the way `env`, `inventory` and `vault` are. Two guards come with it: only one capture runs at a time, and one that never calls back is abandoned after `ns.CAPTURE_TIMEOUT_SECONDS` (180) so the command cannot wedge. `RunCapture` also passes the rest of the slash command through as `args`, which is how `/lootpath capture journal 14` picks the M+ preview level.
- **2026-09-06 - `capture journal` registers in `Modules/Journal.lua`, not `Captures.lua`.** The rule is that a capture calls only functions its own file names, and the journal's list belongs beside the adapter that owns it; `Captures.lua`'s header points at it. `ns.captureOrder` is therefore `env, inventory, vault, journal`.
- **2026-09-06 - The journal capture is the one capture that is not purely a read**, and CLAUDE.md's rule is narrowed rather than broken. `EJ_SelectTier`, `EJ_SelectInstance`, `EJ_SetDifficulty`, `EJ_SetLootFilter` and `C_EncounterJournal.SetPreviewMythicPlusLevel` change the Adventure Guide's **view state** - what the journal is looking at - and nothing about the character, its items or its money. The walk reads the tier, difficulty and loot filter first and puts all three back when it finishes, **including when combat aborts it**. There is no getter for the M+ preview level, so that one cannot be restored: the owner is left with a preview level set in their Adventure Guide until they change it.
- **2026-09-06 - Difficulty IDs come from the client's own `DifficultyUtil.ID`,** with the values read from Blizzard's shipped `DifficultyUtil.lua` as the fallback (`Adapter.DIFFICULTY`). The journal's Mythic+ difficulty is `DungeonChallenge` (8), which is in Blizzard's own `EJ_DIFFICULTIES` list - not a wiki claim.
- **2026-09-06 - Both map-to-journal-instance lookups are recorded side by side, and a map neither resolves is recorded rather than dropped.** `capture journal` runs `C_EncounterJournal.GetInstanceForGameMap(mapID)` and the global `EJ_GetInstanceForMap(mapID)` against the same `GetMapUIInfo().mapID` for every map in `C_ChallengeMode.GetMapTable()`, and `pool.maps[i].resolvedBy` names whichever answered. This is the step §11 calls the most likely to differ from any doc, so the transcript decides it instead of the code assuming it.
- **2026-09-06 - An adapter's list of client functions is names, not values.** A table entry whose value is `nil` is simply absent, so a table of values cannot tell "this client does not have that function" from "not listed" - which is exactly what the capture has to record. `Adapter.FUNCTION_NAMES` is a list of strings and `Adapter.Resolve` looks one up; every real call site still names its function literally, so nothing is ever called because a lookup found it. Found by the test that deletes a function and expects `ok = false`.
- **2026-09-06 - The journal walk reads every target twice, mirroring `EncounterJournal_LootUpdate`.** Blizzard's `EncounterJournal_OnEvent` splits `EJ_LOOT_DATA_RECIEVED` two ways: an event carrying an itemID while the list is current refreshes just that row (`EncounterJournal_LootCallback`), anything else re-reads the whole list (`EncounterJournal_LootUpdate`, an `EJ_GetNumLoot` loop over `GetLootInfoByIndex`). The walk mirrors the second, because it has no frame per row to refresh and cannot come back to a target once the next `EJ_SelectInstance` has moved the journal on. `C_Item.RequestLoadItemDataByID` was the alternative and was **not** taken: Blizzard's own journal never calls it in the loot path, 351 events fired unprompted in the 09-06 walk, and adding a client function nothing has been observed to need is a guess. Both reads are kept in the capture so Tuesday's `capture journal` shows what the second one filled.
- **2026-09-06 - A link-less loot row is `pending`, not "no item level".** 240 of the 376 itemIDs in the 09-06 walk were link-less on *every* row they appeared in; treating a row with no equipLoc as non-gear would silently lose 64% of the map. So a pending row is carried with a nil `itemLevel` and `slot` and `pending = true`, and a row that is known and known not to be gear (a pattern, a mount, a toy - 55 of 613) is dropped the way Inventory drops one. The consequence is deliberate: an item that is a mount in one target and link-less in another stays in the map through the link-less row, because a link-less row cannot be told from gear.
- **2026-09-06 - `Journal` and `Inventory` share one slot table.** The journal's own `EncounterJournalItemInfo.slot` and the row's `GetItemInfoInstant` equipLoc agree one-for-one across all 244 rows of the 09-06 walk that carried both (`One-Hand`/`INVTYPE_WEAPON`, `Held In Off-hand`/`INVTYPE_HOLDABLE`), but the first is the client's localised UI text and the second is not. `ns.Journal` therefore goes through `ns.Inventory.SlotForEquipLoc`, which is what makes M3-3's join between the map and the scanner a join on one vocabulary - QE Live's (extends the 2026-09-06 Inventory decision).
- **2026-09-06 - A boss name is an instance-wide fact.** `EJ_GetEncounterInfoByIndex` answered nothing on every `DungeonChallenge` target and on both Midnight targets in the 09-06 walk, leaving 95 of 613 rows with no boss name in their own target. The aggregator indexes names per instance across every difficulty, which names 73 of those 95; the walk now also calls `EJ_GetEncounterInfo(encounterID)` per row, exactly as Blizzard's loot button does, which the next capture proves for the remaining 22.
- **2026-09-06 - The journal cache is keyed on the build NUMBER**, `GetBuildInfo()`'s second return (69587), not the version string: a hotfix build can move item levels without moving "12.1.0". Every entry from another build is dropped whenever `Build` runs, so a stale map cannot outlive a patch.
- **2026-09-05 - LuaLS gate decides on the JSON report**, not the exit code: `lua-language-server --check` exits 0 either way (measured 2026-09-05), so `tools/luals-check.sh` fails on any diagnostic at Warning or above in `check.json`. CI invokes it as `bash tools/luals-check.sh` and the file carries mode 100755 in git, because a Windows checkout dropped the executable bit and CI failed with "Permission denied" (measured in run 33982979467).

## 12. Working rules (also in CLAUDE.md, shipped in 514)

Branch per issue (`lp-<n>-<slug>`), PR to `main`, never commit to `main` directly, merge your own PR only when every CI check is green. Read the whole Linear issue including its "Working in this repo" section. Verify the issue's premise against the code before building; a wrong premise is reported in the PR and the right thing is built instead - scaling down is fine, widening is not. Never write a measured figure you did not read from a tool. Every guard proven red. Every client read secret-guarded; nothing in combat; no network; **Lootpath never computes a healer value.** In-game steps are the owner's: write the capture, hand it over as human-required, build against the transcript. Report in every PR: what shipped; premise check; measured figures with the tool; guards and how each went red; CI results; left undone, deliberately. **And update this file**: §0 every session without exception, plus whichever numbered section holds the decision, verified fact, refuted premise, or closed issue. A session that only talked still updates §0 if the talk moved anything.

**One worktree per issue, always** (decision 2026-09-06, after two sessions collided in the shared checkout). Before the first edit: `git worktree add C:\Code\lootpath-<n> -b lp-<n>-<slug> origin/main`, then `fetch-libs.ps1` (and `fetch-annotations.ps1` for the LuaLS gate) inside it, because those directories are gitignored. Work, commit, push and open the PR from there; never edit `C:\Code\lootpath` itself while another session may be active; never `git add -A` in a directory you did not create; remove the worktree after the merge. The exact commands are in CLAUDE.md, and every ai-ready issue's "Working in this repo" section points at them.

**Captures and the Encounter Journal.** Captures only read, with one recorded exception: `capture journal` changes the Adventure Guide's view state (tier, instance, difficulty, loot filter, M+ preview level) because the API has no other way to ask for loot, restores what has a getter, and says what it could not restore (§7, 2026-09-06). Nothing any capture calls acts on the character, its items or its money, and no capture calls what a namespace walk finds.
