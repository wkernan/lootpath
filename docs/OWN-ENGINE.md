## The question

The owner, 2026-09-30: "I don't like the fact that a player will have to understand how to set up a server and have it running in the background for this addon to work." Then: "what about going back to building our own engine?" And, on the objection that tuning a healing model needs healing expertise: "I would argue with your help we can figure out these patterns, after all the game mechanics are based off mathematical properties ... Wouldn't it be possible to find and research what is needed for us to roll our own without copywriting anything?" Then: "Go."

Every reload-free design in `docs/REFRESH-WITHOUT-RELOAD.md` still needs a companion program on the player's PC, because QE Live's engine is JavaScript and an addon is Lua with no network and no file reads. An own engine moves the "server" from every player's PC to the maintainer's: tables derived offline, shipped inside the addon as a Data file per patch, scored in Lua in game. Zero setup for the player. This memo says what that costs and where it can fail.

## The answer in one paragraph

**It is possible, the engine itself is small, and the two hard parts are not the ones we expected.** QE Live values a Restoration Druid with a fixed, hand-set stat-weight table per content type, plus Blizzard's rating diminishing returns, plus a per-item effects table - not with a cast model (§1 below). So an own engine is a stats-plus-effects scorer that a set evaluation of 9 microseconds and a search of 12-37 ms can run in the client. What is hard is (1) **where independent weights come from**: the in-game combat log is closed to addons in Midnight, so weights must be derived offline from logs, and Warcraft Logs' API terms forbid shipping derived data in an addon without their written permission; the clean alternative is the combat-log files the client itself writes for the owner and consenting volunteers; and (2) **the effects table**: about 55-60 entries per spec per season, 20-30 hours at a season start and a few hours per hotfix wave, with the flat-heal trinkets being where every public model disagrees with every other. A third thing is not hard but must be said: "agreeing with QE Live" for this spec means agreeing with one expert's hand-set numbers - two of the three public stat guides are written by QE Live's author - so a log-derived engine can legitimately differ, and the promotion bar has to be defined with that in mind. The recommended path is a staged, measured spike whose stage 0 needs no Warcraft Logs at all.

## 1. What QE Live's engine actually is, for this spec (F; read in the fork, `dc6e002b8`)

- **Top Gear for Restoration Druid takes the static-weights branch.** `CastModel.js:96-104` gives the spec a cast function but never sets its `modelType`, so `TopGearEngine.ts:947/957` falls through to the branch that applies Blizzard's rating diminishing returns (`ItemUtilities.ts:593-607`, breakpoints in `STAT.ts:45-51`), a small linear "soft DR" on each weight from the set's total (`:1018-1035`), the effects as stats or HPS, then a weighted sum (`:1040-1082`), minus a fixed penalty for two on-use trinkets (`:1095-1097`). The weights are one constant table per content type (`DruidHealingFocus.js:20-37`). The spec's hand-written cast profile (`RestoDruidProfile.ts`) exists and its own comment says it is "Not used in Top Gear".
- **Every set is scored as fully finished.** A fixed best enchant per slot whatever the item carries (`TopGearEngine.ts:565-634`), gems dealt from one spec list cut to the socket count (`:799`; R-2i found the same), flask, food, oil and vantus as constants (`:754-789`). So the gems and enchants actually on an item do not move its score; only the socket count does. The R-2i gem finding in the brain is the same fact seen from the addon.
- **The Upgrade Finder reruns Top Gear over the worn set plus the one drop** (`UpgradeFinderEngine.js:361-366`) against the worn set alone (`:111`, `:122`), with the tier bonus forced on for both (`forceTier`, `:117`), so a ring drop replaces the weaker ring and a non-tier drop in a tier slot does not lose the set bonus. The percent is `(new - base) / base × modelDiff` (`:373`).
- **Two scale facts the addon has been carrying without knowing:** Top Gear's `scorePercent` carries a constant factor of 1.5 (`modelDiff` for the "Default" model, `TopGearEngine.ts:476`, `CONSTANTS.ts:62`), the Upgrade Finder's `upgradePercent` does not (`UpgradeFinderEngine.js:370` compares `""` to `"Default"` and gets 1); and Top Gear differentials come in steps of about 0.024% because the raw score difference is rounded to whole points before dividing (`:486`; the committed fixtures show steps of 0.024 / 0.048). Neither changes any decision Lootpath makes today (the two scales are never combined, ROADS-UX [R3 2]); both matter for measuring an engine against them.
- **The tier set is a flat multiplier:** +3% for the S2 2-piece, +5.5% more for the 4-piece (`DruidSpecEffects.js:15-21`); the committed Top Gear fixtures carry `topSet.stats.bonusHPS` = 0.085 with the 4-piece (`qe-droptimizer-Hotornot-hdaldwpeakpb.json`), which confirms it. That 8.5% is the single largest effect in the season; the best trinket upgrade in the Upgrade Finder exports is about 2%.
- **What this means.** The thing to reproduce is a linear scorer with DR and an effects table. An engine that reproduces the structure and differs only in the weights will agree with QE Live exactly as far as the weights agree - and the weights are one person's judgement. The measurement in §6 separates the two.

## 2. Where independent weights can come from

### 2a. In game: closed

- `COMBAT_LOG_EVENT` and `COMBAT_LOG_EVENT_UNFILTERED` are `HasRestrictions` (`CombatLogDocumentation.lua.annotated.lua:124-125, 132-133`) **(i)**; the per-event reader exists only in `C_CombatLogSecure`, declared `Environment = "SecureOnly"` (`CombatLogSecureDocumentation.lua.annotated.lua:1-6, 45-47`) **(i)**; the wiki: "This event is no longer accessible to addons in Midnight since Patch 12.0.0 ... Fires ADDON_ACTION_FORBIDDEN when attempting to register this event" **(ii)** https://warcraft.wiki.gg/wiki/COMBAT_LOG_EVENT. Ion Hazzikostas, 2025-11-13: "combat events are in a black box; addons can change the size or shape of the box ... what they can't do is look inside" **(ii)**. This holds everywhere, not only in instances; the press reports of "only in encounters and M+" are about secret values in general, not the combat log.
- What is open out of combat: **Blizzard's own meter, `C_DamageMeter`** - per-source and per-spell healing totals per session, `SecretWhenInCombat` (`DamageMeterDocumentation.lua.annotated.lua:23, 41, 59, 79`) **(i)**, meter types including `HealingDone`, `Hps`, `Absorbs`. No crit flag, no overheal, no events. Enough for a cast profile's shares; not enough for weights.
- The old **Healer Stat Weights** addon (MIT, `notarealwzrd`, last push 2021-01-09, `## Interface: 80300`) **(ii)** computed weights in game by attributing each heal event to stats; its whole input is what Midnight removed. **Its licence is MIT, so its method AND its code may be studied and adapted** - the one healer-weights implementation that is not AGPL or unlicensed.
- Conclusion: weights are derived offline and shipped as data. This is the Mr. Mythical shape (its neural net trained offline on SimulationCraft batches, exported as one Lua data file, forward pass in game; `ModelData.lua` measured at 504,702 bytes) **(ii)**; Mr. Mythical's repo has no licence, so pattern only.

### 2b. Offline, from per-event combat logs: the method, in our own words

WoWAnalyzer (AGPL-3.0) carries the documented method in `BaseHealerStatValues.tsx` and, on older branches, a Restoration Druid module (last commit 2022-08-15; today only Holy Priest subclasses the base) **(ii)**. Its stated goal: "to reveal what your stats were actually worth after an actual real-world fight". Described from reading, copying nothing:

- **Inputs:** the player's heal and absorb events with target, amount, overheal, crit flag and tick flag; damage taken by the player; a stat tracker giving the ratings at the moment of each event (buffs and procs included); rating-to-percent at the current rating with diminishing returns; a per-spell table saying which stats scale each spell (int, crit, haste-by-cast, haste-by-tick, mastery, vers; unknown spells default to crit and vers).
- **Per event** (E effective, O overheal, R = E + O; d/dr = percent per rating point at the current rating): **Intellect** contributes E ÷ Int when O = 0, else 0. **Versatility** E ÷ (1 + v) × dv/dr when O = 0. **Crit**: the expected-value form values the non-crit heal × dc/dr × (critMultiplier − 1), skipping overhealing events. **Haste, cast-time form:** E ÷ (1 + h) × dh/dr for haste-scaling spells, an upper bound that ignores mana; **haste, tick form:** the same restricted to HoT ticks, "typically the better calculation ... for raid encounters where mana is an issue". **Mastery (Harmony):** n = the druid's mastery HoTs on the target at that moment, rebuilt from the druid's own buff apply/refresh/remove events per target; since 11.1 the stacks have diminishing returns, T(n) = [0, 1, 1.7, 2.3, 2.8, 3.2, 3.5, 3.7, 3.8, 3.85, 3.875]; gain = E ÷ (1 + m·T(n)) × T(n) × dm/dr. **Leech:** measured from leech events when the player has the rating, otherwise predicted. **Overheal policy:** an event with any overheal counts for nothing except leech, because "a spell that partially overheals will do the same amount of effective healing regardless of the raw strength of the heal".
- **Aggregation:** sum per stat over the fight; weights = gain ÷ gain_int. The method never values a trinket: procs enter only through the stat tracker.
- **Documented limits:** the values describe that fight; the cast-time haste form is an upper bound; accuracy depends on the tracker knowing every buff.
- **Turned into a shipped profile:** the pipeline extracts per parse, per spell, casts per minute, ticks per cast, targets per cast, healing share, overheal fraction, the marginal effective fraction (E over events with O = 0 ÷ all E), the raw-weighted mastery multiplier, the empirical coefficient (raw per event ÷ Int × vers × mastery × crit factor, cross-checked against spell data); globally the active-time share, mana at fight end, Genesis and cooldown uptimes, the non-scaling share, the fight length, the content band, the hero tree. Aggregated per band with a trimmed mean and a bootstrap confidence interval; **a weight whose interval overlaps another's in rank is not shipped** (SimulationCraft's own scale-factor discipline: warn when "a scale factor is lesser than or equal to its error margin" **(ii)**).
- **The regression alternative** (HPS on stat totals across many parses) is not a primary estimator: healing is capped by damage intake, skill correlates with item level, top players' stats are chosen from guides and are collinear (murlok.io's top-50 haste +1423 and mastery +988 against vers +332 and crit +252 **(ii)**). It is useful for one thing the per-event method cannot decide alone - how much haste becomes more casts versus faster ticks (regress casts per minute on haste, within-player across weeks) - and for sign and ordering checks.

## 4. The effects table: how big the treadmill is (counted from the repo's own data)

- **The journal walk** (`spec/fixtures/captures/Lootpath-20260916-162655.lua:116480-119904`, cache key `69587|18|105|2:8:15:16:23`, Restoration only): 30 targets, 362 rows, 265 sources, 106 distinct items; by slot Trinket 15, Finger 12, Head 9, Neck 8, Off-hand 8, 1H 7, 2H 6, Back 6, Waist 6, Legs 6, Chest 5, Feet 5, Hands 5, Wrist 4, Shoulder 4 **(i)**. (The brain's "478 drops" is the panel's candidate count from the 09-06 walk, a different measure.)
- **The Upgrade Finder exports** (`spec/fixtures/qe/qe-upgradefinder-Hotornot-*.json`, eight files): 357 rows, 315 distinct id@level, 46 trinket rows over 24 trinket IDs per full document; trinkets are mid-table - the best (Soulcoiler Ritual Vessel 270162 at 334, 2.049%) ranks #22 in the Dungeon document and #31 in the Raid one, the top ten are two-handers, Gaze of the Coiled Watcher and a ring, and the four best trinkets sit within 0.17-0.37 points of each other **(i)**. Seven flat-heal trinkets score exactly 0 in every document **(i)** while mythicsim.com gives one of them (Chiral Marrowgrafter) "+5.55% HPS" **(ii)** - the clearest public sign of where models disagree.
- **Classification of the 25 Resto-eligible trinkets (15 from the walk, 10 delve):** 1 passive stat, 5 stat proc (RPPM), 3 stat on-use, 5 flat heal proc, 6 heal or absorb on-use, 4 unique (Gebbo's Bottomless Bag 270164, Wavecaller's Seastone 270167, Hex Lord's Dooming Idol 270169, Ruby Whelp Shell 193757), 1 not in QE Live's data at all. About 21 of 25 fit five generic rules.
- **The generic rules and their public sources:** RPPM proc chance = RPPM × min(time since last attempt, 3.5 s) / 60 with bad-luck protection worth "approximately 13.1% more procs" **(ii)** (Dorovon's gist); on-use average = amount × duration / cooldown times an alignment factor; flat heal = heal × procs per minute × (1 − overheal) × targets; absorb = face value × (1 − waste); effect values scale by item level through a per-level curve. **The error is not in the formulas; it is in the judgement numbers** - overheal share, targets, average stacks - which QE Live sets by hand for almost every entry (F). Estimated error bands (iii): stat procs ±5-10% of the effect (under 0.2% of total HPS); stat on-use ±15-25%; flat heals and absorbs ±30-100% (0 to 5% of HPS, the Chiral gap); unique items ±50-100% (the guides disagree on their order); the tier set ±30% of a 3-8.5% bonus, the largest absolute risk.
- **QE Live's own table, as the honest measure of the treadmill (F):** three layers - datamined coefficients (49 trinkets), one entry per item with hand-picked parameters, and a per-item function that in most cases calls one of about eight generic helpers; current-season 28 trinket entries, about 3 fully special-cased and 3 semi-special; 6 non-trinket effect items; 21 Midnight embellishments. Commits to its effect files in the fork: `Trinkets` 6 / 2 / 17 in June / July / August, the August spike bracketing the 12.1 launch ("Response to the in-game item massacre", 08-18).
- **What Lootpath would maintain, per spec, per season (iii):** about 25 trinkets, 3-6 effect armour pieces, the 6-8 healer-relevant embellishments, one tier pair, 3-5 weapon enchants - **about 55-60 entries**, about 20 needing judgement parameters and about 5 needing their own code; **about 20-30 hours at a season start, then 3-6 hours per hotfix wave** (QE Live shipped three tuning responses within ten days of launch). Every further healer spec adds its tier pair and re-tunes the efficiencies.
- **Tier and Catalyst:** the S2 bonuses (Genesis: HoTs 15% stronger for 8 s on a 15% Rejuvenation chance; the 4-piece guarantees it off cooldowns and extends it) **(ii)** Method; an engine treats tier as a threshold - enumerate the tier masks over the five slots and add the bonus inside each - and must clone catalysable drops as QE Live does (`ItemUtilities.ts:1121-1125`) or say "not modelled". The Catalyst charge is not readable as a currency (`spec/fixtures/captures/README.md`, 09-08).
- **Crafted stats are readable from the link** (modifiers 29 and 30 = `ChangeModifiedCraftingStat_1/2`, `Enum.lua:5526-5527`, in the committed capture at line 121274) **(i)**; whether an embellishment shows as a reagent slot needs one capture (iv).

## 5. The engine, as it would be built (designed against the code; nothing built)

- **Inputs per item** and where each comes from: §3's table. Identity stays `ns.ItemKey`; the stats cache keys by the link without gems or enchant (crafted modifiers survive in the link, `Core.lua:318-324`).
- **The score:** a set value `V(S) = base + w_int · Int + Σ_r w_r · g_r(pct_r(T_r)) + Σ effects + tier(mask)`, where `T` sums the set's stats plus an assumed finish (QE Live's own rule, so the enchant-by-ID table is not needed for parity) and `pct_r` converts rating to percent AFTER summing the set through DR; `w_r` is value per percent point (what logs can give); `g_r` an optional fitted curvature; `base` the healing that does not depend on gear stats (without it, ΔV/V overstates). Because DR, curvature, tier thresholds and stat-scaling effects all depend on totals, **every number shown is a full set evaluation**; the per-item gradient is used only to sort and prune. Upgrade percent the Upgrade Finder way: `100 × (V(best set over worn ∪ {item}) − V(worn)) / V(worn)`, tier forced on, the item allowed any slot it fits. Our percents stay unscaled; the compare command fits and prints QE Live's factor rather than adopting it.
- **Measured cost** (the repo's own Docker Lua 5.1, scratch scripts): **9.18-9.54 µs per full 16-item evaluation.**
- **The search:** QE Live nests every slot and keeps 3000 sets, tractable only because a non-patron pass sees 30 items (`TopGear.tsx:177`). The owner's newest committed capture (`Lootpath-20260916-162655.lua`, inventory read 3, 15 worn) has these candidates per slot: Head 2, Neck 2, Shoulder 4, Back 3, Chest 2, Wrist 3, Hands 1, Waist 5, Legs 4, Feet 4, Finger 5, Trinket 14, 1H 2, 2H 3 - **a full Cartesian search of 1.048 × 10⁸ sets, about 1000 s**: an offline check, never in game. Proposed: drop dominated candidates; enumerate the feasible tier masks (≤ 2⁵); inside each, coordinate ascent from the best item per position over ten single slots, the ring pair, the trinket pair and the weapon combination, every move a full evaluation, constraint-breaking moves rejected (embellishments ≤ 2, vault ≤ 1, Catalyst ≤ charges, unique IDs). **Measured on synthetic inventories:** 5 of 5 seeds matched the exhaustive optimum exactly in 380-784 evaluations (5-11 ms) against 2.9 million sets (32-37 s); **at the real slot counts, 964-2,390 evaluations, 12-37 ms** - three to eight frames at a 5 ms budget, in a coroutine resumed on `OnUpdate`, yielding on `debugprofilestop()` (already used, `Core.lua:473`), stopping under `InCombatLockdown()` and restarting after `PLAYER_REGEN_ENABLED` as RoadsCache defers (`RoadsCache.lua:343-344`). The headless rule: the search must equal brute force on small synthetic inventories.
- **The Upgrade Finder equivalent:** each journal drop at the walk's previewed level (the row carries level and link, `Journal.lua:1015, 1036`), 1-3 evaluations each, about 1,500 evaluations, about 15 ms, computed when RoadsCache rebuilds (`RoadsCache.lua:31-36`, debounce `:40`). Crafted rows: not rated in stages 0-1.
- **The data files:** `Data/EngineWeights.lua` (schema, version, method, `patch`, `derivedAt`, per spec per content type per key band: `baseValue`, `weights`, `curvature`, `assumedBuffs`, `assumedFinish`, `logsUsed`, `fights`, a `castProfile` for provenance, `fitError`; DR brackets only if the client call cannot answer; tier thresholds), `Data/EngineEffects.lua` (`[itemID] = { kind, stat, baseAtLevel, scaling, uptime, confidence = "modelled"|"generic", source }` plus set entries), later `Data/EngineFinish.lua`. Under 30 KB for one spec, about 150 KB for seven. Shipped in the addon package through CurseForge; **a file whose `patch` does not match `GetBuildInfo()`'s version is refused** - `Update Lootpath - its ratings are for 12.1.0, you're on 12.1.5.`; a broken file - `Not rated - the rating data didn't load.` (verb first, reason after a dash, no source, no "plan").
- **The honesty surface:** a provenance line (`From your gear's stats and this patch's healer weights, derived 6 Oct.`, plus the key band); a confidence class per item - `high` (stats only), `medium` (a generic-rule effect), `not rated · effect not modelled` (no number drawn); **never a list that sorts or combines our number with QE Live's** (ROADS-UX [R3 2]); stage 1 is a hidden developer panel (`/lootpath engine`, off unless `db.global.developer.engine`) and chat, no tooltip, glow, Equip Now or map number; stage 2 may show ours for a promoted slot class only, and whether ours ever replaces a stored QE Live number is the owner's decision.

## 6. The measurement: `/lootpath engine compare`

- **Joins:** Upgrade Finder rows by `id@level` against our per-drop percent (`drop` rows only until stats-at-track is settled); Top Gear `asOffered` pass 1 (`QEImport.ForPass`, `QEImport.lua:1092`) with **our search restricted to pass 1's `considered` pool** (else we answer a 55-item question and QE Live a 30-item one); top-set agreement per slot by key, rings and trinkets as unordered pairs; single-item differentials give per-item deltas - 80 of 216 across the 19 committed Top Gear documents.
- **Metrics per slot class** (armour, jewellery, weapon, tier slot, trinket; trinkets and embellished items always apart): n; Spearman ρ (average ranks for ties; not computed under n = 5); top-1 agreement and "ours inside their top 3"; **sign agreement** (the product's own gate, `UFImport.IsUpgrade` at `UpgradeMapPanel.lua:1880`), rows with |QE| < 0.1 left out as ties; MAE raw and after a fitted scale k; k itself. Stored per week in `db.global.engineCompare[weekKey][charKey][ct][keyLevel]`, twelve weeks kept.
- **The yardstick, measured on the committed exports:** QE Live against itself on the same day and content: ρ 1.000, MAE 0.000; Raid one day apart: ρ 0.994-1.000, MAE 0.012; **QE Live's Dungeon export against its own Raid export - the two differ only in the hand-set weight tables - per-slot ρ 0.861-1.000 (Hands 0.861, Wrist 0.879, Finger 0.939), MAE 0.137 points, top-1 misses in Hands and Trinket.** QE Live's mean |upgrade%| is about 0.85 and its median positive upgrade about 0.95%.
- **Proposed promotion bar per slot class:** at least 3 distinct weeks and both content types; pooled n ≥ 30; median per-slot ρ ≥ 0.97 and minimum ≥ 0.90; top-1 (within 0.1 points) ≥ 90%; sign agreement ≥ 95% outside the dead zone; MAE after k ≤ 0.07 points (half of QE Live's own raid-versus-dungeon gap); k varying under 10% across weeks; any week below the floor demotes the class. **Justification:** an engine that disagrees with QE Live more than QE Live disagrees with itself across content types would visibly change recommendations; one that disagrees less is inside the noise of one expert's judgement.
- **Separating the two error sources - the "structure run":** fit weights to QE Live's own Upgrade Finder rows (regress `upgradePercent` on each drop's stat difference) and compare; a high ρ there with a low ρ on log weights says the disagreement is the weights, not the engine. The fitted weights are never shipped; the exports are the owner's own runs on his fork, and comparing outputs is using facts (§2c).
- **Headless guards:** the committed exports; a synthetic weights file labelled as such; an item-stats fixture the `GetItemStats` stub answers from once the capture lands; compare deterministic twice; the patch refusal; compare never writes `qeImports` or `ufImports`; DR monotonic; search equals brute force; the sign constants read, never re-derived. Each proven red.
- **Trinkets:** reported, never gated on at first; QE Live's number or "not scored" stays on screen for them.

## 8. What this memo settles, and what it does not

**Settled:** the engine is small and the client can feed it; the weights cannot be derived in game and must ship; Warcraft Logs is research-only without permission; the client's own log files and the MIT method are a clean source; QE Live's Resto Druid engine is hand-set weights plus effects, so the yardstick is one expert's judgement and the bar must be set against QE Live's own cross-content variance; the effects table is about 60 entries and a real per-patch cost; nothing here breaks the licence of anything.

**Not settled, and only running it can settle:** whether log-derived weight ratios land inside the bar; whether Restoration Druid's healing is complete in Midnight's advanced log; the confidence intervals at N parses; the haste split; whether hero trees need separate profiles; the point cost of a Warcraft Logs query; every (iv) above.

**The honest recommendation:** stage 0 is worth its two weeks because it costs no licence, no permission and no promise - the weights loader, the score, the compare command and the structure run prove the engine's shape against exports the addon already holds, while the owner records his own logs and RPGLogs answers an email. What the compare says after three weeks is the decision; not this memo.
