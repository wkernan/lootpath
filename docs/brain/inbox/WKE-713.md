# WKE-713: E-5b, the combat-log weights tool reads each healer spec from its own module

## §0
**As of 2026-10-19, E-5b (WKE-713 built, PR open on branch
`wkernan/wke-713-e-5b-the-combat-log-weights-tool-reads-each-healer-spec-from`:
`tools/combatlog`'s Restoration-only spell table, Harmony constants and buff
lists moved from `lib/spells.js` into `tools/combatlog/specs/restoration.js`,
behind a new `specs/index.js` registry keyed by the client's spec ID.
`lib/attribute.js` and `lib/entry.js` no longer import Restoration's table or
constants by name: they resolve the found player's spec module once per
`walk()` (`findPlayerSpec`, up front, so Harmony's cross-unit aura tracking
has it from the log's first `COMBATANT_INFO` batch regardless of member
order) and read her role, primary stat, stat list, spell table and buffs
through it. A second healer spec is a new module beside `restoration.js` and
one more line in `specs/index.js`'s `SPECS` map, not a change to either
`attribute.js` or `entry.js`.)**

No second spec was added - none of this tool's spell-to-stat data exists for
any healer besides Restoration (105), and inventing it without a captured log
and SimC `spell_query` evidence would break the method's clean-room rule
(`docs/COMBAT-LOG-WEIGHTS.md` §0). The ticket's premise was read as: make the
module boundary real so a second spec, once captured, is data - not that this
PR captures or fabricates one.

`probe.js` (the Harmony/crit-multiplier diagnostic against a log's own
ticks) was left reading Restoration's module directly
(`require('../specs/restoration')`) rather than dispatching by spec ID: its
own logic names Harmony and her stack table throughout, not just her
constants, so generalizing it has no second spec to generalize against yet
and would be guessing a shape. It is scoped narrower than "the combat-log
weights tool" (`weights.js`, `lib/attribute.js`, `lib/entry.js`) that the
ticket names.

Proof the refactor changed no output: `weights.js` run over the committed
`spec/fixtures/combatlog/WoWCombatLog-20261017-AltarOfFangs-12.txt.gz` before
and after, same `--derived-at`, diffed byte for byte - `EngineWeights.combatlog.lua`
and `combatlog-weights.json` both identical. All 40 `tools/combatlog` tests
(`node --test`) still pass, including `test/writer.test.js`'s own
byte-identical-across-two-runs check and the Lua-side `EngineScore.Load`
round trip.

## §6 Architecture
A line in the `tools/combatlog/` row (the table under "6. Architecture") now
reads stale: it says "The spell-to-stat table is `lib/spells.js`". That table
is `tools/combatlog/specs/restoration.js` now, reached through
`specs/index.js`'s spec-ID registry rather than imported directly by
`lib/attribute.js` or `lib/entry.js`. The rest of that row (the method, the
written files, the test count) is unchanged by this PR.
