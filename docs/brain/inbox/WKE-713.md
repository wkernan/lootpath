# WKE-713: E-5b, the combat-log weights tool reads each healer spec from its own module

## §0
**As of 2026-10-19, E-5b (WKE-713 built, PR #369 on branch
`wkernan/wke-713-e-5b-the-combat-log-weights-tool-reads-each-healer-spec-from`:
`tools/combatlog/lib/attribute.js`, `lib/entry.js` and `lib/estimate.js` name
no spell, buff or spec. Restoration's spell table, buffs, constants and
Harmony's mastery tracker moved from `lib/spells.js` into
`lib/specs/105-restoration-druid.js`, found through
`lib/specs/index.js`'s registry (`get(specID)`, `ids()`); `lib/spells.js`
stays as a one-line re-export of the new module's names, so
`test/spells.test.js`, `test/probe.test.js`, `lib/probe.js` and `probe.js`
(Restoration-only by nature, left untouched) keep working unchanged.
Harmony's per-target aura tracking left `walk()` for the module's
`mastery.createTracker(player)` (`onCombatantInfo`/`onAura`/`onUnitDied`/
`diag()`); the mastery formula itself left `attribute()`'s mastery branch for
`mastery.gain(E, pct, tracker, dst, C)`. A second healer spec whose mastery
fits that same tracker/gain shape is a new module beside Restoration's plus
one registry line, not a change to `attribute.js` or `entry.js` - its spell
rows still have to come from a real `spell_query` capture (§0's clean-room
rule), which is a later ticket; none was added here. A toy spec
(`test/fixtures/toy-spec.js`, two spells, a flat-multiplier mastery) proves
the shape instead, registered only inside `test/specs.test.js` through the
registry's test-only `register()`/`unregister()`.**

**Decision 8, from the first code review round (PR #369): `lib/entry.js`'s
`specOf()` collects every usable segment's spec ID across every walked log
and throws, naming all of them, when more than one appears - so two logs of
different specs passed to one `weights.js` run refuse rather than one
silently labelling the other's segments.**

## §7
**2026-10-19, E-5b (WKE-713, the owner's words, from the ticket): "Outcome:
`tools/combatlog` keeps everything Restoration Druid-specific in one spec
module behind a small registry, so adding Holy Priest, Mistweaver or any
other healer later means adding one module file. Today's Restoration output
stays byte-identical." Decided: the module's exported shape is `identity`,
`spellRow`/`ROWS`/`UNKNOWN`, `constants`, `buffs`, `mastery` (a tracker plus
`gain`); `lib/spells.js` stays as a re-export rather than being deleted, so
nothing outside `attribute.js`/`entry.js` has to change; a toy spec, not a
real second one, proves the interface, because a real second spec's `ROWS`
needs `spell_query` output the owner's Windows machine produces, not this
VM - that capture is a later ticket. Not decided here: which real spec comes
next, or whether a mastery formula unlike Harmony's (not a stacking-aura
count) needs the tracker/gain contract widened - the ticket's Decision 2
leaves that for whichever spec needs it.**

## §6 Architecture
A line in the `tools/combatlog/` row (the table under "6. Architecture") now
reads stale: it says "The spell-to-stat table is `lib/spells.js`". That path
is still correct as a file that exists (the re-export), but the table itself
now lives in `tools/combatlog/lib/specs/105-restoration-druid.js`, reached
through `lib/specs/index.js`'s registry rather than imported directly by
`lib/attribute.js` or `lib/entry.js`. The rest of that row (the method, the
written files) is unchanged by this PR; the test count there (40) should
read 47 once this is folded in.
