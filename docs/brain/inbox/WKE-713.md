# WKE-713: E-5b, the combat-log weights tool reads each healer spec from its own module

## §0
**As of 2026-10-19, E-5b (WKE-713 built, PR open on branch
`wkernan/wke-713-e-5b-the-combat-log-weights-tool-reads-each-healer-spec-from`:
`tools/combatlog`'s Restoration-only spell table, Harmony constants and buff
lists moved from `lib/spells.js` into `tools/combatlog/specs/restoration.js`,
behind a new `specs/index.js` registry keyed by the client's spec ID.
`lib/attribute.js` and `lib/entry.js` no longer import Restoration's table or
constants by name: they resolve the found player's spec module once per
`walk()` (`findPlayerSpec`, up front, so Harmony's cross-unit aura tracking
has it from the log's first `COMBATANT_INFO` batch regardless of member
order) and read her role, primary stat, stat list, spell table and buffs
through it. A second healer spec whose mastery is shaped like Harmony's (a
count of the player's own stacking auras on the target) is a new module
beside `restoration.js` and one more line in `specs/index.js`'s `SPECS` map,
not a change to either `attribute.js` or `entry.js`. One formula is not
generalised: `lib/attribute.js`'s mastery branch still assumes that shape,
only its inputs (stack factor, coefficient, base points) come from the spec
module - a spec whose mastery isn't shaped that way needs that branch
generalised first, which IS a change to `attribute.js`.)**

**Rework (same day): a code review found `buildEntry`/`specOf` silently
merged two different specs' logs into one entry, labelled after whichever
walk's segments were usable first - reproduced with
`.stokowski/artifacts/probe-mixed-specs.js` (a stub second spec registered at
runtime; `specOf` returned 105 or 902 depending only on argument order, and
both orders' `Dungeon` band `10` weights were identical, meaning both specs'
segments landed in the same band regardless of which label won). Fixed:
`specOf` now collects every usable segment's spec ID and throws, naming all
of them, when more than one appears. Reran the probe after the fix: it now
throws `mixed specs in one run: 105, 902 - one entry is one spec` in both
argument orders. Added three tests: `test/entry.test.js` (the mixed-spec
throw, both orders, and that two agreeing logs still resolve), and two in
`test/attribute.test.js` (a spec named explicitly with no registered module
throws, and a second registered stub module is dispatched by ID rather than
Restoration's table - confirmed red by temporarily hardcoding the dispatch to
Restoration's import, then reverted).

A second self-review (`/code-review`) then caught a regression the first
fix's own shape introduced: `specID`/`specModule`/`C` in `lib/attribute.js`
were resolved once, as `const`, from the log's first `COMBATANT_INFO` of the
player's - unlike `ratings`/`ciInt`/`buffs`, which already re-read every one
of hers. Before this PR the spell table was spec-invariant (always
Restoration's), so this never mattered; once it is spec-dependent, a log
spanning a respec would keep attributing every later segment through the
first key's spec module. Fixed: `specID`/`specModule`/`C` are `let`, still
seeded up front from `findPlayerSpec` (so cross-unit Harmony tracking has a
module from the start, per the ordering fix above), but now re-resolved
(`resolveSpec`) on every later `COMBATANT_INFO` of the player's, same as her
ratings. Added a fourth test (`test/attribute.test.js`, two keys in one log,
spec 105 then a stub): confirmed red first (`git checkout --` the file,
rerun - `105 !== 902`), then green after reapplying the fix.

A third review pass (two independent `/code-review`-style agents) found one
more real gap in that same fix's shape: `specModule`/`C` now re-resolve live
on every `COMBATANT_INFO` of the player's, but `seg.spec` (the label
`specOf`/`buildEntry` read) is set once, at the segment's first heal, and
never updated - so a spec change inside an already-open segment (no
`CHALLENGE_MODE_END`/`ENCOUNTER_END` between the two `COMBATANT_INFO`
batches) would attribute later heals under the new spec while still
labelling the whole segment the old one, uncaught by the cross-segment guard
above (it only compares `seg.spec` across already-closed segments). Fixed:
inside the `ci.guid === player` branch, if the segment already has a heal
attributed (`seg.ratings` set) and this `COMBATANT_INFO` names a different
spec than the one every heal so far used, `walk()` now throws
(`spec changed from <old> to <new> inside one open segment (<kind>: <name>)
- one segment is one spec`) instead of blending two formulas silently.
Confirmed red (temporarily removed the one `if` line, reran the new test -
"Missing expected exception"), then green after restoring it. Checked the
real committed Altar of Fangs fixture's own four same-spec mid-segment
`COMBATANT_INFO` re-fires (gear/proc stat refreshes, not a spec change) still
pass clean.

Two further findings from the same passes were triaged and left alone,
deliberately:
- `lib/entry.js`'s `render()` still writes the literal string "Restoration
  stat weights" into the generated Lua header. True today (Restoration is
  the only module) and wrong the day a second spec's entry is written -
  changing it now would also change Restoration's output, which this PR's
  own title commits to keeping byte-identical. Left as is, with a comment
  above `render()` explaining why, to fix when a real second spec exists to
  word it for.
- `findPlayerSpec` now throws immediately (`no COMBATANT_INFO names
  <GUID>'s spec`) when an explicitly-named `--player` GUID has no
  `COMBATANT_INFO` at all, where the pre-refactor code would only fail later,
  on the first heal of hers (`a heal of the player's... before any
  COMBATANT_INFO`) or not at all if she also has zero heals
  (`buildEntry`'s "no usable segment in the logs"). Judged an improvement
  (fails faster, names the GUID), not a regression; neither path had test
  coverage before or after.
- `specOf(walks)` is still computed twice (once inside `buildEntry`, once by
  `weights.js` for `buildTable`'s `specID`) - the same cosmetic duplication
  this PR's first review round already flagged as sub-threshold. Left alone
  again, same reasoning: real but negligible cost on a developer-only tool
  over a handful of logs.

Full suite: 46/46 pass (`node --test` in `tools/combatlog`, up from 40 before
this rework); re-verified byte-identical against the pre-refactor code
(`git archive` of the commit before this PR's first commit) on all six
committed fixture logs individually AND run together in one `weights.js`
call, not just the one fixture checked in the first round.**

No second spec was added - none of this tool's spell-to-stat data exists for
any healer besides Restoration (105), and inventing it without a captured log
and SimC `spell_query` evidence would break the method's clean-room rule
(`docs/COMBAT-LOG-WEIGHTS.md` §0). The ticket's premise was read as: make the
module boundary real so a second spec, once captured, is data - not that this
PR captures or fabricates one.

`probe.js` (the Harmony/crit-multiplier diagnostic against a log's own
ticks) was left reading Restoration's module directly
(`require('../specs/restoration')`) rather than dispatching by spec ID: its
own logic names Harmony and her stack table throughout, not just her
constants, so generalizing it has no second spec to generalize against yet
and would be guessing a shape. It is scoped narrower than "the combat-log
weights tool" (`weights.js`, `lib/attribute.js`, `lib/entry.js`) that the
ticket names.

Proof the refactor changed no output: `weights.js` run over the committed
`spec/fixtures/combatlog/WoWCombatLog-20261017-AltarOfFangs-12.txt.gz` before
and after, same `--derived-at`, diffed byte for byte - `EngineWeights.combatlog.lua`
and `combatlog-weights.json` both identical, on every committed fixture log
individually and all six run together. All `tools/combatlog` tests
(`node --test`; 40 before this rework's five added, 46 after) still pass,
including `test/writer.test.js`'s own byte-identical-across-two-runs check
and the Lua-side `EngineScore.Load` round trip.

## §6 Architecture
A line in the `tools/combatlog/` row (the table under "6. Architecture") now
reads stale: it says "The spell-to-stat table is `lib/spells.js`". That table
is `tools/combatlog/specs/restoration.js` now, reached through
`specs/index.js`'s spec-ID registry rather than imported directly by
`lib/attribute.js` or `lib/entry.js`. The rest of that row (the method, the
written files) is unchanged by this PR; the test count there (40) should
read 46 once this is folded in.
